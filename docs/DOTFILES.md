# Dotfiles y fidelidad

La auditoría recorre una lista delimitada de componentes detectables: Hyprland, Caelestia, Quickshell, Fish, Fastfetch, Neovim, terminales, temas GTK/Qt, lanzadores, multimedia, autostart y unidades de usuario. No copia todo ~/.config. Excluye cachés, dependencias regenerables, historiales y nombres sensibles. Los enlaces se registran sin recorrer sus destinos automáticamente.

Las configuraciones Hyprland clásicas se analizan para resolver `source =` y variables estáticas. Las Lua se analizan para `require` literal dentro de las raíces conocidas. No se evalúa Lua ni Fish: el hyprland.lua real contiene funciones que crean archivos y por ello ejecutarlo durante una auditoría sería incorrecto. Un require dinámico, una dependencia externa o una ruta construida queda marcado para revisión. Los imports de Neovim se conservan junto a lazy-lock.json; ni lazy.nvim ni LSP se instalan al auditar.

`capture` vuelve a comprobar los hashes del inventario antes de copiar. Si el archivo cambió, se excluye y hay que repetir audit. Se conservan bytes, saltos de línea y permiso ejecutable; no se normalizan temas o reglas. Fish universal variables se excluye completamente: puede contener secretos. Plugins y variables no sensibles requieren exportación revisada por separado. No se ejecuta Fastfetch porque sus módulos `command` pueden ejecutar comandos; se guarda su formato original, incluida la función Fish de saludo.

Caelestia: se conservan custom-schemes, shell.json, overrides Lua y Fish, esquemas generados y secuencias de color. Se registran dependencias instaladas y procedencia local de shell/cli/Quickshell. Los archivos de aplicación distribuidos por paquetes se recuperan desde una fuente revisada, evitando copiar indiscriminadamente sus cachés o árboles de depuración. La inspección no demuestra modificaciones en todos los archivos distribuidos por un paquete; revisa ese código antes de prometer equivalencia visual completa.

El wallpaper activo se descubre mediante el enlace documentado de Caelestia y se guarda como recurso privado. También se guardan referencias de SDDM (configuración, metadata, configuración de tema y licencia si existen). Los recursos se extraen en `staging/…/resources/<sha>/nombre`, nunca a una ruta activa. No se activan SDDM, wallpapers o monitores desde estas referencias. Fuentes locales, iconos, temas y otros fondos se inventarían con conteos, tamaños y licencias encontradas; no se incorporan a Git sin revisión de cada recurso.

Un archivo con monitores/HEADLESS, código Lua, servicio, autostart o Sunshine queda `manual_review`. El plan mantiene ese bloqueo aunque el archivo esté en la captura. Los includes de configuraciones no portables propagan la necesidad de revisión. Para activar esas configuraciones, revisa las copias aisladas y realiza una restauración manual controlada en destino. No existe una opción global que convierta todos los archivos pendientes en seguros.
